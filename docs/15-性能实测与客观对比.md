# 性能实测与客观对比

## 15.1 测试环境与方法论

**环境**：Windows 11 x64，Intel 16 核 CPU，NVIDIA RTX 5060 Ti 16GB（GPU 路径可用，但其相对 CPU 的优势因矩阵乘优化而收窄，见 15.3），64GB 级内存。

**方法论（全部可复现）**：

1. Scourge 计时用语言内建 `now`（单调时钟），只包裹目标计算，不含编译/构造时间；
2. 每个数字至少重复 2–3 次，书中给出区间；
3. Python 对照用 `time.perf_counter`，同机同进程顺序执行；
4. 数值结果做交叉验证：Scourge 与 Python 对同一公式的输出必须逐位一致（已验证：矩阵乘 `sum` 均为 `13106430.75`，`fib(30)` 均为 `832040`，1000 万次循环累加均为 `49999995000000`）；
5. 不挑数据：VM 慢于 CPython、AOT 中大尺寸矩阵乘慢于 VM 的数字**原样收录**。

**未尽事项**（诚实声明）：单机单次会话测量，未控制 CPU 频率波动；未做 CPU 绑核；矩阵乘未做分块优化对比；numpy 使用 OpenBLAS 默认线程配置。这些因素会让绝对值随机器变化，但量级关系稳健。

## 15.2 矩阵乘：Scourge vs 纯 Python vs numpy（CPU）

测试程序：`verify/probes/t17_bench.sg`（128×128）、`t18_bench_224/256/512/1024.sg`（各尺寸，固定公式生成数据）、`bench_py.py`（Python 对照，同公式）。

| 尺寸 | 实现 | 耗时（ 复测） | 相对 AOT 倍数 |
|---|---|---|---|
| 128×128 | **Scourge AOT（build）** | **0.32–0.35 ms** | 基准 |
| 128×128 | Scourge VM（run） | 1.23–1.38 ms | ≈4.1× 慢 |
| 128×128 | 纯 Python 三重循环 | 115.2 ms | **≈340× 慢** |
| 128×128 | numpy 2.5.1（OpenBLAS） | 1.61 ms | ≈4.7× 慢 |
| 224×224 | Scourge AOT | 1.23 ms | — |
| 224×224 | Scourge VM | 6.21–7.28 ms | ≈5.4× 慢 |
| 256×256 | Scourge AOT | 1.87 ms | — |
| 256×256 | Scourge VM | 20.2 ms | ≈10.8× 慢 |
| 512×512 | Scourge AOT | 15.5 ms | — |
| 512×512 | Scourge VM | 311.6 ms | ≈15.8× 慢 |
| 1024×1024 | Scourge AOT | 139 ms | — |
| 1024×1024 | Scourge VM | 3214 ms | ≈23× 慢 |
| 1024×1024 | numpy 2.5.1（参考） | 7.72 ms | ≈56× 慢（numpy 更快） |

读法：

- **对纯 Python 循环：约三个数量级的优势**（128² AOT 0.32ms vs 115ms ≈ 340×）。张量运算是语言内建、走原生运行时，且 AOT 路径已向量化内联（见 15.2.1）。
- **对 numpy：小尺寸 Scourge AOT 反超（128² 0.32ms vs 1.61ms ≈ 5× 快），大尺寸 numpy 碾压**（1024² numpy 7.72ms vs Scourge AOT 139ms ≈ 18× 快）——numpy 的 OpenBLAS 多线程分块在 1024² 起全面发力。诚实结论：**Scourge 矩阵乘小尺寸领先 numpy，大尺寸被其多线程实现碾压，且仍没有任何张量库生态**。
- **VM 与 AOT 在矩阵乘上现在 AOT 全面更快**：AOT 比 VM 快 4–23×（见 15.2.1）——矩阵乘就用 AOT。

### 15.2.1 AOT 矩阵乘的优化：行流式向量化内联

AOT 矩阵乘的早期实现曾在 256² 起、AOT 比 VM 慢 1.3–1.5×（根因：内联展开的 `store-to-load` 依赖链阻断寄存器累加与自动向量化）。现实现改为**行流式 i-k-j + `__restrict` + 4-wide 向量化**后全面反超。以 `now` 隔离纯计算段实测（必须排除 1MB+ 字面量解析时间，否则会掩盖差异）：

| 尺寸 | VM (ms) | AOT (ms) | AOT 比 VM 快 |
|---|---|---|---|
| 128² | 1.23–1.38 | 0.32–0.35 | ≈4.1× |
| 224² | 6.21–7.28 | 1.23 | ≈5.4× |
| 256² | 20.2 | 1.87 | ≈10.8× |
| 512² | 311.6 | 15.5 | ≈15.8× |
| 1024² | 3214 | 139 | ≈23× |

读法：

- **全尺寸 AOT 一致快于 VM**：向量化内联使 AOT 在所有尺寸上压过 VM 4–23×——矩阵乘就用 AOT。
- **但 AOT 仍远落后于 numpy 大尺寸**：1024² AOT 139ms vs numpy 7.72ms（numpy 约 18× 快）。Scourge 矩阵乘是单线程朴素实现，没有 OpenBLAS 的多线程分块——这是下一步优化方向。
- **更大尺寸与 GPU 的关系见 15.3**：N1 修复后 CPU AOT 已极快，GPU 仅在 ≥1024² 起才有微弱优势。

## 15.3 矩阵乘：CPU vs GPU

`build --gpu` 已验证可用（第 16.7 节），数值与 CPU 逐位一致。CPU AOT 已极快，GPU 的相对优势被大幅压缩——同机实测：

| 尺寸 | CPU AOT | GPU AOT | GPU/CPU |
|---|---|---|---|
| 224×224 | 1.23 ms | 113 ms | **0.01×**（GPU 慢约 92×） |
| 512×512 | 15.5 ms | 110 ms | **0.16×**（GPU 慢约 6.3×） |
| 1024×1024 | 139 ms | 121 ms | **≈1.15×**（GPU 仅微弱领先） |

读法：

- **小矩阵（≤512²）GPU 反而远慢于 CPU AOT**：GPU 有固定的驱动加载 + 数据往返开销（约 100ms 级），小负载被这个常数吃掉。
- **大矩阵（≥1024²）GPU 才勉强领先**：1024² GPU 121ms vs CPU AOT 139ms，仅约 1.15×。要看到 GPU 的显著优势，需要比 1024² 更大的矩阵（GPU 的并行算力才压过其固定开销）。
- **回退机制**仍有效：文档声称的 `SCOURGE_NO_GPU=1` 永久回退 CPU、任意失败自动回退，本书已验证（GPU 二进制在 `SCOURGE_NO_GPU=1` 下回落到 CPU 路径，数值不变）。

**建议**：除非矩阵 ≥1024² 且追求极限吞吐，否则 CPU AOT 已更快更省事。GPU 路径仍是正确性验证的亮点（双模逐字节一致），但性能卖点已让位于 CPU AOT。

## 15.4 标量代码：AOT 的数量级优势

测试程序：`verify/probes/t19_scalar.sg`（1000 万次循环累加 + fib(30) 递归），Python 对照为同算法 CPython 3.14.6。

| 负载 | Scourge VM | Scourge AOT | CPython 3.14 | AOT vs CPython |
|---|---|---|---|---|
| 1000 万次循环累加 | 1212 ms | **11.87 ms** | 882 ms | **≈74× 快** |
| fib(30) 递归 | 908 ms | **6.78 ms** | 159 ms | **≈23× 快** |
| VM vs CPython | 1.37× 慢 | — | — | — |

读法：

- **AOT 模式是真正的原生代码**：标量循环比 CPython 快 1–2 个数量级，符合"编译到 LLVM IR + -O2"的预期。fib(30) 的 134 倍 VM→AOT 提升（908→6.78ms）说明解释开销在递归这种"调用密集"负载上尤其沉重。
- **VM 模式是一台直白的字节码解释器**：1000 万次循环比 CPython 慢 1.37 倍，fib(30) 慢 5.7 倍。这是客观事实——CPython 有二十多年的解释器优化（内联缓存、特化字节码），Scourge VM 是直译路线。**结论：调试用 VM，发布用 AOT；不要把 VM 数字当作语言的性能上限。**
- 附带一个正面数据：`examples\train_linreg.sg`（3000 epoch × N=24 的线性回归，纯 Scourge 张量运算）在 VM 模式下总计 4.56ms——张量路径即使在 VM 下也走原生运行时，小规模训练负载完全可用。

## 15.5 编译耗时：AOT 的另一半代价

| 源文件 | 矩阵元素数 | 构建耗时 |
|---|---|---|
| 128×128（165KB） | 2×16K | **5.8 s** |
| 256×256（657KB） | 2×65K | **9 s** |
| 512×512（2.6MB） | 2×262K | **~20 s** |
| 1024×1024（10.5MB） | 2×1M | **~9 s** |

> 构建时间随字面量元素数线性增长（1024² 约 9s）。**即便如此**，把 1024×1024 矩阵写死进源码仍是反模式——生产代码应从文件/计算加载张量数据。

## 15.6 与官方文档性能声称的核对

| 文档声称（04 §11） | 本书实测 | 结论 |
|---|---|---|
| 1024×1024 GPU 299ms vs CPU 4618ms（15.4×） | GPU ~121ms / CPU ~139ms（≈1.15×） | **官方加速比已过时**（CPU AOT 大幅优化后）；GPU 路径本身有效 |
| run/build/GPU 四模式逐字节一致 | run/build 一致；GPU 数值逐位一致 | 验证通过 |
| AOT 与 run 双模逐字节一致 | **验证通过**（t16_dual_mode） | 证实 |
| 张量运算 VM/AOT 同档 | **验证通过**（15.2） | 证实 |
| 中大尺寸 AOT 矩阵乘更快 | **成立：AOT 比 VM 快约 4–23×** | 本书复测确认（15.2.1） |

## 15.7 性能结论（四条，不多不少）

1. **发布场景选 AOT 做标量**：标量代码比 CPython 快 23–74 倍；代价是数秒起的编译时间。
2. **矩阵乘用 AOT 显著更快**：AOT 比 VM 快 4–23×；纯 Python 循环慢约三个数量级，numpy 小尺寸被 Scourge AOT 反超、大尺寸以多线程碾压 Scourge。
3. **GPU 仅极大矩阵有用**：GPU 仅在 ≥1024² 起有约 1.15× 微弱优势，≤512² 反而比 CPU AOT 慢；除非追求极限吞吐，CPU AOT 已足够。
4. **调试场景用 VM**：保存即跑、REPL、mcp 全走这条路；标量比 CPython 慢 1.4–5.7 倍，但张量运算仍走原生例程，小型数值程序完全可用。
