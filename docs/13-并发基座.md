# 并发基座

## 13.1 现状：同步执行，类型恒等

```python
async def double(x):
    """async 函数：P0 阶段 await 为类型恒等，函数同步执行。"""
    return x * 2

async def pipeline(x):
    y = await double(x)
    z = await double(y)
    return z

def main():
    # await 只能出现在 async def 内（否则报 E2010）
    print(pipeline(3))      # 12
    return 0
```

`pipeline(3)` 返回 12：`double(3)=6`，`double(6)=12`。计算正确，但**没有任何并发发生**——`await` 在类型检查器里是恒等变换（操作数类型透传），函数体同步执行到底。

这不是 bug，是路线图的第一个台阶：语法基座（`async def` / `await` / 位置检查）先落地并冻结语义边界，真正的 Task 语义随后续迭代进入。对使用者的含义很直接：**今天可以写 async 函数，但不要期待任何并行加速**；把并发留给未来的版本，现在的代码按同步语义推理即可。

## 13.2 唯一硬规则：E2010

`await` 只能出现在 `async def` 函数体内。在普通函数里写 `await x` 报 E2010_AwaitOutsideAsync：

```
error[E2010]: await 只能出现在 async def 函数体内
```

这条检查保证了解释器不需要处理"在非协程中挂起"的复杂情形——语义边界在编译期就画好了。

## 13.3 为什么先放"空转"的 async

一种常见的语言演进策略是**先冻结语法、再填充语义**：`async def` 的签名规则、`await` 的位置规则、与 `Result`/panic 的交互规则，全部在这一步定死；后续并发实现（Task、调度器、channel）在不破坏现有程序的前提下填进来。已经写好的 `async` 代码在未来获得真正的并发语义时不需要改写——只要它本来就按"可能有并发"的方式写（不依赖求值顺序的副作用）。
